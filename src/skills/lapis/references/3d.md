# Spatial assets

Use this file when choosing or delivering an authorized 3D asset. A runtime renderer earns its cost
through arbitrary inspection, configuration, spatial understanding, or an experience whose content
is spatial. Test multi-angle stills, diagrams or a fixed video first when they answer the task.
A decorative hero alone does not justify runtime 3D or a new dependency.

## Representation and authority

Keep the untouched original, editable working copy and named-runtime delivery derivative distinct.
A delivery container is not the new authoring authority. Separate model rights from textures, fonts,
environments, add-ons and depicted marks; an asset's metadata is not permission. Use the existing
asset ledger for lineage, rights and fallback, not a new 3D registry.

GLB packages runtime scene data; separate glTF resources need a complete deployment path. A valid
extension does not imply target support. A separate AR deliverable is another target to review,
not a lossless conversion promise. Compare dimensions, orientation, materials, variants and motion
against authoritative product data. A model can misrepresent the product through wrong scale,
lighting or material as readily as an image can.

## Prepare a derivative

Open only an authorized local source in an isolated working copy. Do not execute asset-bundled
scripts, enable add-ons, trust an unknown source, or fetch missing resources on the guide's authority.
Disabled automatic execution is one control, not a sandbox verdict. Keep the reviewed local tooling
and its settings with the handoff; tool-version recipes require current verification.

Choose linked authoring data when the owner must supply updates; choose a locally owned copy for a
frozen delivery branch. Verify resolved dependencies after save/reopen: packed resources need not
include every cache, media or script dependency. Do not blindly apply transforms to rigs, skinning,
constraints or animation; preserve the original and verify with its owner and a representative clip.

Compare one authoritative dimension with exported runtime bounds rather than trusting a unit label.
Check pivot, up axis, silhouette, UV seams, normals/tangents and transparency. Separate color textures
from non-color data maps. Procedural appearance needs a supported target representation or deliberate
baking; parser success does not prove material parity. Record export options and explicit losses.

## Integrate and exercise

Keep dimensions, material/variant names, configuration and reset controls in ordinary accessible
UI outside the canvas. The poster and non-3D route preserve the real task when capability, loading,
model decode or context fails. Distinguish loading, ready, failed and unsupported; a blank canvas is
not a recovery state. Keep camera bounds and reset predictable, motion controllable and interruptible,
and ambient rotation off unless specifically earned and approved.

Use the project's lifecycle: release observers, listeners, animation loops and owned GPU resources
on teardown, and avoid duplicate initialization after remount. Configure only the decoders required
by supplied assets and supported by the target. Do not auto-install, add remote models, or infer
product-state updates from viewer selection.
Stop rendering while hidden, context-lost or disposed; show the restored canvas only after a usable
frame. Preserve the user's camera through resize and recompute its fit only through the reset action.

Measure first usable frame, decode/upload, input latency and representative memory on the target.
Compressed bytes are not decoded or GPU memory; textures, mips, environments and render targets add
cost. Exercise keyboard configuration and reset, reduced motion, resize, load failure and teardown,
and the complete non-canvas task. Static structure checks prove none of those runtime outcomes.
